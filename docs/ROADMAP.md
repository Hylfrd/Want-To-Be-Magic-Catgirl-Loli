# 项目交付路线图｜Main → Submain → Subsession

日期：2026-10-12。依据：[DRD v1.0](DRD.md)、[协作规则](../AGENTS.md)、[full subsession 协议](FULL_SUBSESSION.md)。本次交付是规划，**全部实现任务尚未开始，未启用 full subsession，也未创建执行会话**。当前仓库只有设计与协作资料；历史设备准备不能代替本路线图的实际会话、路线或精度验收。

本图覆盖 DRD 的完整 v1，并单列已经确定方向的 v1.1；未来候选不混入 v1 承诺。任务最小单位是一项可独立委派、交付和复核的完整 Agent 工作包，不拆成函数、单个控件或机械测试列表。正式运行时，Submain 再按实际上下文与文件所有权拆分其内部工作。

## 1. 交付终点

| 交付层 | 完成标准 |
| --- | --- |
| 软件可测试交付 | 单服务器 API＋Worker＋C++ 内核、管理网页、Android APK；素材到发布到手机闭环；八类路线及未知／失败状态；固定参照 AR、恢复、缓存延续、TTS；受控 OCR／云端增强；构建与部署说明及必要验证证据 |
| v1 验收完成 | 软件交付之外，DRD §7 的真实短路线 AR、恢复、性能和数据行为有证据；AI 辅助录入与导航提示的效果比较有实际记录。失败项如实保留，不用模拟、编译或 Agent 声明替代 |
| v1.1 后续交付 | 同一 C++ 内核经 JNI 在已下载区域离线选目的地／重规划，版本和结果一致；不引入第二套 Java 规则 |

Main 对照原需求逐项验收，只有对应层要求全部满足才宣布该层完成。人工结果未返回时，可完成独立软件工作并交付“待现场验收版本”，不能宣称整个 v1 已验收。

保持已选技术栈：Python／FastAPI、SQLite＋文件目录、单 Worker；Recast／Detour v1.6.0＋Boost.Graph Dijkstra＋薄 C ABI／ctypes；Vue 3／TypeScript／Vuetify MD3＋Three.js；Java／XML／Material Components＋ARCore；CPU PP-OCRv5 mobile＋北京百炼 qwen3-vl-plus。具体兼容依赖在相应首次实现任务中锁定，遵循 DRD 的已有依赖授权，不新增其他服务或框架。

不在本路线图实施：自动精确视频重建、全校园精度承诺、持续口袋定位、手机 AI、实时电梯调度、泛化无障碍认证、完整离线 AI、A*、综合偏好权重或新的类别。后续候选只经明确设计变更进入任务。

## 2. 会话组织与所有权

| 角色／ID | 模型与强度（正式启用时） | 负责工作包 | 文件责任 |
| --- | --- | --- | --- |
| Main | gpt-6.1-sol / xhigh | 原需求、依赖、配额、Git、跨线验收 | 根计划、总览、注册表及集成协调；通常不写产品代码 |
| SM-D 数据与服务 | gpt-6.1-sol / xhigh | D01–D08、I01–I03、H01–H03 协调 | 服务、存储、导入、AI、部署与总集成 |
| SM-N 导航 | gpt-6.1-sol / xhigh | N01–N04、V11-N | C++ 内核、格式、规则、几何及性能 |
| SM-W 管理网页 | gpt-6.1-sol / xhigh | W01–W03 | 管理网页、编辑与预览 |
| SM-A Android | gpt-6.1-sol / xhigh | A01–A05、V11-A | APK、采集、缓存、定位、AR、语音及 JNI 客户端 |
| 执行／集成／审阅 Subsession | gpt-6-luna / max | 下文每个工作包一个责任会话 | 只修改分配的文件；向所属 Submain 交付证据 |

这些是角色名和未来分工，不是已存在的会话。启用前 Main 在 `runtime/full-session/<goal-id>/` 建立协议规定的状态并填入真实 IDs。每个工作包只设一个实现者；审核人员不重复实现或新增验收门槛。同一线的工作可能落入同一文件，Submain 必须先分配互不冲突的路径；无法分开则串行。目录责任是模块边界，实际路径由 D01 根据空仓库确定一次，不授权重构已有布局。

四个 Submain 同时存在时，执行／审阅会话共最多 **7** 个：`1 Main + 4 Submain + 7 worker = 12`。初期只启动 SM-D／SM-N／SM-A 所需角色；网页准备就绪时再启用 SM-W。配额按阻塞链移动，由 Main 明确回收／重新分配，不能各线自行累计九个 worker。待启动、集成和审阅也占槽位，归档不证明运行已停止。

所有工作在现有 `main`，不创建分支、tag、issue、PR、worktree 或替代 clone。Main 持有全局 Git 协调责任；每次 staging／commit 给唯一写入者明确窗口。只暂存自有路径，实现与 AI 记录分开提交。任务完成边界才由 Main fetch 并审阅**整个** outgoing range，确认所有夹杂任务均已完成且有推送授权，再一次正常 push；不能发布其他任务的未完成 checkpoint。

## 3. 阶段交付与并行推进

阶段表示能力门槛，**不是全项目串行瀑布**。满足启动依赖即可开发，阶段验收只等待必要的真实交付依赖。启动依赖允许使用已确定接口和标注模拟的响应；最终交付必须接真实模块。

| 阶段 | 门槛与阶段产物 | 可提前并行的工作 |
| --- | --- | --- |
| G0 契约与可审核输入 | D01＋D02：版本化对象、包／API／ABI 细节、坐标样例、可追溯模拟场景；H01 条件清单 | D03 服务基础、N01 内核构建、W01 网页、A01 APK 与设备预检；不等校园采集 |
| G1 导航与服务 | D03–D05＋N01–N04：审核地图构建、复用句柄、八类可追溯路线、资源与状态错误 | W02 地图编辑、A02 地图路线、A03 对齐，可按固定契约先使用模拟包 |
| G2 管理发布闭环 | D06＋W01–W03：空数据库建图、导入候选、修正、校准、审核、不可变发布、客户端下载 | D07／D08 AI、A04／A05；导航与网页后续联调不用等待云密钥 |
| G3 手机导航闭环 | A01–A05＋D05：采集上传、地图比较、真实参照定位与 AR、失跟踪／跨层／后台、缓存与语音 | I01 部署与集成、I02 性能；H02 测量可与设备预检提前准备 |
| G4 真实验收与 v1 交付 | I01–I03＋H01–H03：单机运行包、正确性与性能、真实 AR／恢复、AI 费用与实际效果对比，逐项结论 | 已测小区域先闭环；复杂跨层与地形仍可标注模拟，不等全校园建图 |
| G5 v1.1 离线重规划 | V11-N＋V11-A：同内核、兼容包、JNI、本地选目的地／重算与一致性 | v1 稳定且版本基线已验收后启动，不阻塞 v1 软件可测试交付 |

建议启动波次（依赖完成即滚动，非固定日期）：

1. D01 与 H01 准备；D01 定案后 D02、D03、N01、W01、A01 同时推进。
2. D02／N01 完成后 N02；D03 完成后 D04、D06 的存储接口部分；W02、A02／A03 使用契约样例开发。
3. N02 后 N03；D04 后 D07；D06 和 N04 成品接入 D05／W03／A02。D08 可在 D07 的固定调用接口上独立实现预算与降级，再接真实供应商。
4. A03 后 A04；A02 后 A05。I01 开始组装真实各线交付，I02 与人工 H02／H03 的准备并行，已有设备能力尽早小范围预检。
5. 独立软件行为验收后交给 H02／H03；AI 分析返回证据、完成 I03。通过与失败分别记录，再决定 v1 结论；随后按确定方向推进 G5。

主要风险链：`D01 → D02 → N02 → N03 → N04 → D05 → I01 → I02/I03`；真实 AR 链为 `D01 → A01 → A03 → A04 → H02 → I03`，同时需要 D06 的真实包和 A02 的真实路线。设备不兼容、现场证据缺失或供应商授权阻塞对应分支，其他分支继续。

## 4. 可委派工作包

每项任务共同合同：初始 `status=planned`、`actual_owner=null`、`commits=[]`、`evidence=[]`；接单后填入责任会话与已确认文件范围。下表的工时为**单 Agent 主动工作粗估**（多数约一小时，复杂任务可能跨一至两个上下文），不含排队、下载、返修、现场或审批等待，不是完成时限或实测效率。超过可交付边界时由 Submain 在原范围内拆分，不按计时器强行结束。

所有输出都含：可运行／可审阅文件，实际构建／验证命令及结果、验证版本、模拟／真实标签、剩余阻塞、精确任务拥有提交列表。启动依赖是可以开始实现的最小前提；“交付依赖”必须全部满足才能被 Submain 接受。

## 7. 调度、阻塞与交接合同

正式启用后的 Main 入口：先读本路线图与协议，在共享 `state_root` 填写 goal／overview／plan，再将ID、状态、配额和文件所有权落入各 medium 项。父子会话保留立即父ID和root ID；派发时只给当前工作包及必要契约，不重复灌入全仓库、原聊天与修复长日志。

每次委派使用这个合同（填真实值，不用下方占位符直接启动）：

```text
role: Submain 或 Subsession；task_id: <本图ID>
protocol: docs/FULL_SUBSESSION.md；state_root: runtime/full-session/<goal-id>/
root_id / parent_id / session_id: <真实会话身份>
scope: <本图交付目标与明确owned paths>；exclusions: <不扩范围>
inputs: <DRD小节、契约与依赖交付的精确路径／版本>
startup_dependencies / delivery_dependencies: <对应表项>
quota: <Main已保留槽位>；models: <协议角色设置>；cap: 12 total
topology: 独立侧栏会话，无隐藏替代；existing main only；no child push
acceptance: <表中行为及应提交证据>；status: ready
git_writer: <当前窗口持有人或未授予>；先申请窗口，不能见空暂存区就写
return: ID/status、需求、base/final main、exact owned commits、evidence paths、blockers/next action
```

状态按 `planned → ready → running → submitted → accepted`；出现依赖或外部条件缺失则 `blocked`，说明具体条件与继续工作范围，不冒充完成。提交本身只到 submitted；Submain 复核确切版本和组合行为后才接受，Main最终检查原需求。

默认新增测试为零，先复用已有检查／直接验证。若出现实际验证缺口，先说明保护的具体要求、既有检查缺口与最小必要验证，再补聚焦检查；不增加CI、框架、coverage门槛或测试数量目标。计划中的必需行为验证不授权通用测试平台。

同一问题两轮修复失败，由Submain重评估并按协议做限定修复／上报；不引入已删除的假死监控、自动会话替换或后台守护流程。工具不能提供协议要求的会话／角色能力时记录限制，不暗中更换拓扑。需要用户决策的分支保留阻塞，继续独立工作。

本任务可视化存于仓库内 `local-visualizations/`，在 `.gitignore` 排除，作为本地交互视图；**本文件是可共享的权威计划**。可视化展示工作包、阶段和依赖，不作为任务执行或验收数据库。后续变更先更新本文件，再同步视图。
